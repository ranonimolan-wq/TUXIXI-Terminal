# Bug Fixes — TUXIXI Terminal

| Date | Module | Symptom | Root cause | Fix |
|------|--------|---------|------------|-----|
| 2026-11-23 | input / gui | AltGr characters (e.g. `@`, `{`, `}`, `$` on European layouts) reached the shell as ESC-prefixed meta bindings; zsh then redrew lines and executed vi/meta commands, so typed letters "appeared in places the user never typed" (report: stray characters, `command not found: $s`, floating `n`) | X11 reports AltGr as combined CONTROL+ALT; `encode_char` treats alt as the meta prefix, so ctrl+alt+char was encoded as ESC+char | `input::strip_altgr` strips ctrl+alt for plain character keys (logo combos preserved); applied in the GUI keyboard handler before shortcut checks; unit-tested in `input::tests` |
| 2026-11-23 | settings | Default font (11px) rendered far smaller than mainstream terminals; existing configs kept the tiny size forever | Old default persisted into config.json on first launch and was re-applied on every load | Default bumped 11px -> 15px (96dpi parity with common terminal defaults); one-time migration rewrites legacy `font_size: 11` on load; custom sizes untouched |
| 2026-11-22 | gui | GLX BadMatch (12297) crash at startup on Intel/NVIDIA mixes | glutin-winit GLX-first display path kept the GLX display alive and failed at context creation; EGL never tried | EGL-first 9-rung init ladder (EGL desktop -> EGL ES 3.0 -> GLX desktop) + software-GL re-exec fallback; panicking config picker caught per rung |
| 2026-11-23 | vt / gui / shell | "Ghost input": characters the user never typed appeared on the prompt line (only zsh, not bash); screenshots showed e.g. 8 rendered `s` while zsh executed `sss` — the displayed line contained older, differently-colored glyph runs mixed with the current line | Root causes: (1) the hand-written VT never answered cursor-position queries (DSR/CPR, CSI 6n), so shells/plugins querying the terminal could not resynchronize their cursor model and their partial redraws landed on wrong rows/columns; (2) the child inherited an arbitrary (often empty) TERM, degrading the shell's redraw strategy; (3) tracked modifier state could go stale after focus changes | Replaced the emulation core with `alacritty_terminal` (CPR/DA/color responses flow back to the PTY as `TermEvent`s), pinned `TERM=xterm-256color` + `COLORTERM=truecolor` in the session environment, reset tracked modifiers on focus loss and dropped synthetic key events; verified on Xvfb with real zsh + syntax-highlighting: displayed text now matches the shell buffer byte-for-byte |
| 2026-11-24 | gui / clip | "Copy from TUXIXI, paste into Firefox does not work" while paste INTO TUXIXI worked; Alacritty's select-then-paste flow worked everywhere (report: 128 MB RAM also questioned) | Root causes: (1) mouse drag-release stored the selection NOWHERE (no PRIMARY, no CLIPBOARD) — only the explicit Ctrl+Shift+C shortcut ever wrote CLIPBOARD, and arboard does not implement PRIMARY at all, so the mainstream select-then-paste flow could never work; (2) "1.7 MB" Alacritty comparison was a measurement artifact — real Alacritty measured 125.0 MB RSS under the identical Xvfb/software-GL conditions (TUXIXI 114-120 MB, same stack) | Replaced arboard with copypasta (the X11 selection stack used by mainstream Rust terminals): drag-release now stores BOTH PRIMARY and CLIPBOARD (documented in handler.rs), middle-click pastes PRIMARY, OSC 52 `Selection` routes to PRIMARY; pasteboards are long-lived process-wide owners (`src/clip.rs`); verified end-to-end on Xvfb with xclip reads of both selections |
